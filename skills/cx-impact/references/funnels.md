# Quantitative sales funnels

Sales funnels are a separate document kind, not CJM stages interpreted as analytics. They use the existing standalone renderer and shared appearance controls. Node.js 18+; no server or runtime packages.

```sh
node skills/cx-impact/scripts/render-map.mjs --check skills/cx-impact/examples/funnels/online-sales.en.json
node skills/cx-impact/scripts/render-map.mjs skills/cx-impact/examples/funnels/online-sales.en.json /tmp/online-sales.html
node /tmp/online-sales.source/rebuild.mjs
```

Within an installed package, omit the `skills/cx-impact/` prefix. `--check` creates no files, exits nonzero on invalid data or failed geometry, and does not establish visual or semantic acceptance. Delivery includes HTML, exact adjacent JSON bytes, checks and a source snapshot. Keep the HTML, JSON and `.source` folder together for rebuilding. Standalone HTML requires none of those adjacent files to run.

## Version 1 contract

Top-level fields are `version:1`, `kind:"sales-funnel"`, `locale:"en"|"ru"`, required nonempty `title`, `subtitle`, `disclaimer`, `scope`, `sources`, `stages`, and optional `transitions`, `repeat`. Unknown fields are rejected in this quantitative contract to prevent unsupported units or money from silently disappearing. Ordinary version 1 maps retain their existing contract.

- `scope`: `{unit:"people",entry:"closed",cohortStart,cohortEnd,asOf,timezone,conversionDays,identityRule,orderRule}`. Dates are real `YYYY-MM-DD` dates; timezone must be recognized by `Intl.DateTimeFormat` as an IANA timezone (e.g. `Europe/Moscow`). `conversionDays` is finite and positive, maximum 36500. All conversions use the same closed, ordered entry cohort. The cutoff must be at least `cohortEnd + conversionDays`; open first-purchase windows are unsupported. Dates represent authored civil-date boundaries in the stated timezone; arithmetic uses calendar-day differences, not elapsed-hour/DST claims. Define the boundary convention in `orderRule` when necessary.
- `sources`: 1–100 `{id,label,text,kind}` records. Kind is `user-input`, `requirement`, `research`, `runtime`, `code`, or `other`. IDs match `[a-z][a-z0-9_-]*` and are unique within each list. Every stage, node, edge and repeat module has a nonempty `sourceIds` array of existing distinct source IDs. Sources describe the basis; listing one does not verify its truth.
- `stages`: 2–12 ordered `{id,title,count,sourceIds,definition}` records. Counts are nonnegative safe integers or explicit `null` for unknown. Known counts cannot increase, including across missing stages. Counts are independently authored people aggregates. The final stage represents first paid purchase when repeat is supplied; state that definition explicitly.
- `transitions` (optional): `{scope,nodes,edges}`. This is a separately authored DAG, never inferred from stage differences. Scope is required: `{stageId,rootTotal,denominator,description}`. `stageId` references a known-count stage; `rootTotal` must equal that count and the sum of graph root values. Thus the graph represents the complete population at the referenced subset stage (checkout in the examples), not an undeclared smaller sample. `denominator` and `description` are human-readable, required text.
- Graph `nodes`: 2–32 `{id,title,value,sourceIds,stageId?,outcome?}`. Graph `edges`: 1–48 `{id,from,to,value,label,sourceIds}`. Values are nonnegative safe integers. Roots have no incoming edges, sinks have no outgoing edges; the supplied edge list explicitly establishes these boundaries. Isolated nodes, invalid references, cycles and self-edges are rejected. Retry is an unrolled node. All sinks must have `outcome:"progress"|"lost"|"pending"|"unknown"`; internal/root nodes cannot claim final outcomes. Incoming and outgoing sums independently equal each node value wherever that side has edges. A node's optional `stageId` is an authored association, not a claim that its value equals the whole stage. Graph scope is the enforced aggregate equality.
- `repeat` (optional): `{eligible,purchased,pending,windowDays,sourceIds,definition}`. Integer counts; finite positive `windowDays` up to 36500. `eligible + pending` equals the known final first-purchase count. `purchased <= eligible`. Repeat rate is `purchased / eligible`, never all entrants and never immature first purchasers. Eligible cannot be positive before even the earliest first purchaser could have matured (`cohortStart + windowDays`). Pending must be zero once even the latest first purchaser has matured (`cohortEnd + conversionDays + windowDays`). Between these bounds, authored eligibility is accepted and clearly not independently verified. `pending` here means immature repeat windows; graph pending is a separate supplied first-purchase outcome.

No monetary fields are supported. Revenue, currencies, refunds and order-versus-person denominators need a separate explicit contract; a people funnel cannot establish financial effect. Counts cannot establish identity resolution, event order, cohort membership, maturation or causality without underlying records. No emotions or causal explanations are inferred.

## Rates and geometry

`assets/funnel-core.js` is UMD (`CXFunnel` in the browser, CommonJS/Node export). `validateFunnel(data)` returns the original input or throws a field-path error. `analyzeFunnel(data)` returns stage copies with `entryDenominator`, `previousDenominator`, `fromEntry`, `fromPrevious`, `notProgressed`; graph roots/sinks/order/outcome totals plus node/edge rates; optional repeat `rate`; semantic `limits`. Rates are ratios, not percent numbers. Missing counts or zero denominators yield `null`, shown as Unknown. First-stage previous and residual metrics have `previousApplicable:false`: displayed as an entry/not-applicable dash and exported as `not_applicable`, distinct from a missing measurement (`unknown`). Internal ratio fields remain null.

Stage `notProgressed` is the immediately previous known count minus this known count, only when both adjacent counts exist. It is explicitly “not progressed within window”, not loss. The viewer does not fill missing intermediate denominators using earlier known stages.

`layoutFunnel(data)` returns `{analysis,stages,flows,width,height,geometry}`. Stage rectangles use a single `740 / entryCount` scale (zero if unavailable); unknown/zero bars have zero width. Flows use `520 / rootTotal`, one scale for all node heights and ribbon widths. Per-node incoming/outgoing ports stack in supplied edge order; roots and sinks retain authored order. Sinks are placed in the final DAG column. Zero flows have `width:0,path:null` and explicit zero text/ledger entries. Natural dimensions grow with the DAG. Geometry reports finite extents and detects ribbons intersecting nonincident node bodies; such graphs fail CLI check/render and should be split or restructured. Ribbon crossings are not joins. Crossings, labels and visual readability still need browser review; an arbitrary DAG is not guaranteed a collision-free layout.

## Viewer and exports

Stages, Flows and Table all consume the same analysis. Sources and definitions open with keyboard Enter/Space; Escape closes the dialog and restores focus. The HTML also displays cohort rules and the repeat module. Absent transitions show an explicit no-data message and leave Stages/Table usable. Fit fits width; 100% is the reading size. Large graphs may scroll horizontally or vertically.

SVG exports the selected visual view, including title, scope, definitions, repeat, complete edge label/count/rate ledger, source legend and disclaimer. Table disables SVG with an explanation; use CSV. JSON export preserves exact UTF-8 source bytes, including formatting and trailing whitespace; direct programmatic `renderMap(data)` without source bytes uses deterministic pretty JSON. A snapshot includes all renderer imports, even those used by another document kind, and rebuilds byte-identically.

`funnelCSV(data)` exports RFC 4180 quoted CSV with CRLF rows, raw counts, ratios, denominators, explicit unknown markers, stage residuals, graph scope, repeat pending/window and source IDs. Authored text beginning with a spreadsheet formula operator (including after whitespace/control characters) gets a leading apostrophe. Downloaded JSON is the canonical exact original; CSV contains the documented safety prefix.

The optional finite graph walkthrough is off on load. It only follows supplied nonzero edges, pauses at branches, and stops at sinks. Multiple roots are explicit choices. It is an explanatory traversal, not simulation, elapsed time or traffic speed. Reduced motion uses static next selection. Theme changes presentation only.

The original synthetic RU/EN examples use 10000 / 4000 / 1000 / 600 / 420 people, June 1–7 2026 entry, seven-day first purchase, `Europe/Moscow`, September 1 cutoff. Checkout splits into 420 progress, 150 supplied loss, 20 pending, 10 unknown. Recovery is 140 → 100 retry / 40 lost, then 100 → 60 paid / 30 lost / 10 unknown. All 420 first purchasers have matured for the 60-day repeat window; 105 / 420 = 25%. These numbers are authored examples, not publication inputs from private analytics.
