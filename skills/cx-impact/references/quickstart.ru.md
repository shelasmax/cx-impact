# CX Impact: первое использование

В этом руководстве три небольших вымышленных упражнения для продакт-менеджеров и аналитиков. Пути к исходным данным и скрипту ниже указаны относительно каталога установленного навыка `cx-impact`. Запускайте команды из этого каталога. Примеры сохраняются в отдельный соседний каталог `../cx-impact-first-use-output`; при желании замените его на каталог своего проекта. Храните готовые карты и настроенные снимки отдельно от установленного навыка.

JSON по ссылкам — подготовленные авторские примеры, а не записи запуска агента. Вставка промпта в Codex запускает настоящий эксперимент: карта может отличаться, оставаясь корректной. Сравнивайте разметку доказательств, неизвестные и топологию, а не буквальные формулировки.

Проверить авторский JSON без записи файлов можно так:

```sh
node scripts/render-map.mjs --check examples/first-use/target.ru.json
```

Команда завершается с кодом `0`, только если прошли проверка структуры и автоматическая проверка геометрии. Некорректная структура или ошибка геометрии дают код `1`. Для структурно корректной карты JSON-отчёт выводится в stdout; ошибки валидации — в stderr. Режим проверки не записывает файлы. Рендеринг создаёт HTML, соседний JSON, отчёт проверок и каталог `.source/` для воспроизводимой сборки.

## 1. Создать целевой сервис по требованиям

Исходный материал — **Продуктовый бриф · 2026-08-18**:

> Внутренний сервис должен позволять сотруднику запросить переносной набор для воркшопа через интранет. В запросе должны быть дата и название команды; запрос нужно сохранить и передать координатору. Координатор должен проверить доступность, записать решение и через интранет отправить либо подтверждение с местом получения, либо сообщение о недоступности. Для подтверждённого запроса стойка выдачи должна подготовить и передать маркированный набор и записать выдачу. После воркшопа сотрудник должен вернуть набор на ту же стойку; стойка должна принять его и закрыть запись о выдаче. Часы выдачи и порядок действий при позднем возврате не определены.

Скопируйте этот промпт в Codex:

```text
$cx-impact
Создай компактную карту целевого состояния по вымышленному материалу ниже. Используй русский интерфейс и русский авторский текст, 4 общих этапа, представления CJM, сервисного чертежа и процесса. Обозначь планируемое поведение как требования, необязательные улучшения как предложения, а неподтверждённый опыт, частоту и финансовые эффекты как неизвестные. Покажи обе ветки доступности. Сохрани два отсутствующих правила как явные вопросы и ограничения этапов. Подготовь редактируемый JSON и автономный HTML в локальном каталоге результатов.
```

```sh

```

Проверьте метки требований во всех трёх представлениях, ветки «доступен / недоступен» в процессе, неизвестные часы выдачи и поздний возврат. Пример описывает только намерение. Он не подтверждает реализацию, наблюдаемое поведение, эмоции клиентов, частоту спроса, финансовый эффект или пользу предложений. Успешная проверка покрывает только структуру и автоматическую геометрию.

## 2. Описать текущий процесс по документу

Исходный материал — **Операционный регламент · 2026-07-10**:

Координатор не отправляет подтверждение до завершения проверки и затем пишет либо о возможности получить набор, либо о его недоступности. Регламент не устанавливает срок ответа. Для доступного набора сотрудник расписывается на бумажном листе у стойки ресепшен и получает маркированный набор; строка таблицы остаётся учётной записью выдачи. Позже сотрудник возвращает набор на ресепшен, где сотрудник ресепшен помещает его обратно в запас. Регламент не описывает поздние возвраты.

Затронутые ячейки ответа, узлы и переходы тоже показывают неизвестный порядок подтверждения; сохранённый граф описывает связи из документов, а не установленную последовательность выполнения. Пример не определяет, какой документ действует, соблюдается ли какое-либо правило и что испытывают клиенты. Он не добавляет частоту, финансовый эффект или измеренный результат предложений. Автоматическая проверка не может разрешить смысловое противоречие или подтвердить приемлемость для людей.

Пример заметки об изменениях для авторского результата:

- Базовая версия: `examples/first-use/current.ru.json`; исходный источник `ops-handbook` сохранён без изменений.
- Добавлен ID источника: `customer-faq`.
- Изменены элементы с сохранением ID: `response-timing`, `response-authority`; поля action/channel/evidence/frontstage этапа `review`; `send-collection`, `receive-unavailable`, `available`, `unavailable` и `collection-to-sign`. Каждое затронутое утверждение теперь показывает неизвестный порядок подтверждения и оба источника. Обновлена датированная метаинформация карты.
- Добавленные предметные ID: нет. Удалённые ID: нет. Все ID этапов, участников, дорожек, узлов и переходов сохранены.
- Не разрешено: какой документ задаёт срок подтверждения, соблюдается ли какое-либо правило, фактический опыт клиентов, частота и финансовые эффекты.
- Проверка: структура и автоматическая геометрия проходят; вынесенные подписи полностью показаны под процессом. Визуальный вид, взаимодействия, экспорт, воспроизводимая сборка и человеческая приёмка этим авторским примером не проверены.

Для собственного обновления сохраните исходный сгенерированный пакет. Используйте новое имя результата или скопируйте настроенный снимок в новый каталог ревизии с прежним базовым именем, чтобы относительные пути его сборки продолжили работать.
