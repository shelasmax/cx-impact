# Синтетическая оценка в Codex

[English version](evaluation.md)

Разделение повторных попыток, технических проверок результата и человеческого суждения опирается на понятия из [руководства Anthropic по оценке агентов](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). В этом протоколе смысловое качество оценивают люди; модель не используется для приёмки результата.

Этот протокол сравнивает полный релизный пакет CX Impact с коротким запросом на четырёх оригинальных синтетических задачах картирования. Это исследовательская парная оценка артефактов, созданных в независимых новых сессиях Codex. Она не является исследованием клиентов, универсальным бенчмарком моделей и сред или доказательством общего превосходства одного варианта.

Четыре входных задания являются публичными синтетическими материалами. Подготовленные рабочие каталоги, запросы, логи модели, stderr, созданные артефакты, оценки, заметки рецензентов и наборы для рецензирования храните локально за пределами репозитория. Это сырые данные оценки, а не материалы для публикации. Не публикуйте сводное утверждение о превосходстве до человеческой проверки артефактов.

## Дизайн

Два варианта, четыре задачи и два повтора дают **2 × 4 × 2 = 16 независимых сессий**.

- **Полный пакет (`skill`):** новый рабочий каталог содержит полный пакет CX Impact из разрешённого списка релиза в `skill/`. Агенту предлагается прочитать `skill/SKILL.md` и использовать ресурсы пакета.
- **Короткий запрос (`short`):** в новом рабочем каталоге нет пакета CX Impact, руководства по формату или готового примера. Агент получает только общую инструкцию и запрос конкретного задания.

Оба варианта получают одинаковый `input.md`, а для обновления — одинаковый `base-map.json`. Общая инструкция требует английский результат, сохранение исходных файлов, разделение подтверждённых утверждений, предложений и неизвестных, а также `output/map.html` и `output/map.json`; для обновления дополнительно требуется `output/changes.md`.

Для обоих вариантов используйте одну и ту же явно указанную модель, уровень рассуждения, версию Codex CLI, песочницу и конфигурацию инструментов. Каждая сессия получает новый каталог без истории диалога. В первом повторе runner запускает `short`, затем `skill`; во втором — `skill`, затем `short`. Поэтому порядок вариантов чередуется внутри каждой задачи. Сбой или тайм-аут остаётся результатом запуска и не заменяется новой попыткой незаметно.

Сравнивается полный пакет и короткий запрос, включая инструкции, справочники, ресурсы, renderer и готовые рекомендации. Это не сравнение только двух текстовых абзацев.

## Задачи

Манифест заданий находится в [cases.json](../tests/evaluation/cases.json). Входные файлы содержат только исходные тексты и запрос пользователя; в них нет рубрики или ожидаемых ответов.

| Задание | Явный режим | Отличительная трудность |
|---|---|---|
| `incomplete` | TARGET / TO-BE | Концепция портала дизайн-ревью описывает целевой процесс из четырёх этапов, но не задаёт сроки и работу с новой версией. |
| `current` | CURRENT / AS-IS | Два согласованных документа описывают основной путь пропуска посетителя, ветку закрытой даты, восстановление при несовпадении документа и возврат пропуска. |
| `conflicting` | CURRENT / AS-IS | Два документа о бронировании зала расходятся во времени подтверждения и оплаты депозита; авторитетный источник не задан. |
| `update` | Обновление CURRENT / AS-IS | Полная существующая карта должна сохранить стабильные ID и источники, добавить сведения о запросе и чек-листе и показать новый конфликт о возврате ключа. |

Все сценарии вымышлены и не связаны с примерами велосипеда и первого использования набора для воркшопа. В них нет медицинских, юридических или финансовых бизнес-рекомендаций.

## Подготовка и запуск

Требуются Node.js 18+, Python 3.10+, текущая установленная версия Codex CLI и рабочая авторизация Codex. Runner не настраивает и не меняет авторизацию.

Выберите новый локальный каталог за пределами репозитория. Замените буквальный заполнитель `MODEL` на модель, которая действительно доступна в текущей установке Codex, затем подготовьте 16 рабочих каталогов:

```sh
python3 -B scripts/evaluate-codex.py --prepare /tmp/cx-impact-evaluation --model MODEL --effort xhigh
```

Подготовка отклоняет уже существующий каталог. Для отдельной оценки выберите новое имя каталога; не удаляйте и не перезаписывайте предыдущий запуск ради повторного использования имени. До запуска проверьте `manifest.json`: 16 уникальных попыток, восемь на вариант; выбранные модель и уровень рассуждения; хеши пакета; задачу, вариант и повтор; хеши входов и запросов.

Запустите подготовленные сессии последовательно с лимитом 600 секунд на сессию:

```sh
python3 -B scripts/evaluate-codex.py --run /tmp/cx-impact-evaluation --timeout 600
```

Запуск можно продолжить для попыток с уже созданным `result.json`: при повторной команде их результат сохраняется, а runner переходит к ещё не начатым попыткам. Одну подготовленную попытку можно выбрать через `--trial TRIAL-ID`. Если внешний процесс прерван после записи `started.json`, но до создания `result.json`, сохраните это свидетельство; не удаляйте маркер и не запускайте попытку заново незаметно. Отметьте попытку как прерванную, при необходимости запустите остальные неначатые ID по одному, а любой повтор оформите отдельно в новом подготовленном каталоге.

Runner записывает статусы завершения, сбоя и тайм-аута; код выхода; прошедшие секунды; версию и команду Codex; доступные данные о токенах; базовое наличие артефактов; сохранность входов; `humanReview: not_reviewed`. Тайм-аут или ненулевой код процесса приводит к ненулевому коду runner, но результат всё равно остаётся в знаменателе из 16 попыток.

Runner разработки использует текущий установленный исполняемый файл Codex с явными флагами, эфемерным выполнением, игнорированием пользовательской конфигурации, отключёнными plugins/hooks/apps, экспериментальным флагом `skip_host_skill_discovery` и песочницей `workspace-write`. Эти меры улучшают сопоставимость, но не создают герметичную изоляцию. Установленный CLI может по-прежнему показывать навыки хоста вопреки флагу; проверяйте диагностику запуска, а не предполагайте, что поиск отключён. Оба варианта работают в одной командной среде хоста, а глобально доступное поведение или читаемые пути могут зависеть от установки. Проверяйте логи на загрязнение и записывайте ограничения среды. Не меняйте глобальную конфигурацию в ходе оценки.

В запросе агентам запрещены сеть и другие проекты. Не обещайте доступность браузерных инструментов и не считайте отсутствие браузера самостоятельным сбоем. Самостоятельный HTML можно позже проверить в доступном локальном браузере. Запишите, какой браузер и какие проверки действительно использовались.

Наличие артефакта и чтение JSON — механические наблюдения, а не оценки качества. Сохраняйте stderr и частичные результаты сбоев и тайм-аутов. Не перезапускайте неудобный результат с тем же ID. При отклонении от протокола сохраните исходный результат, а дополнительную попытку опишите отдельно.

Рекомендуется отдельно показать результаты запусков, а распределение качества считать только по проверенным людьми артефактам с явным знаменателем. Дополнительно покажите консервативный показатель завершения по всем восьми подготовленным попыткам каждого варианта. Не смешивайте сбой с нулевой оценкой качества: это разные результаты.

## Человеческая проверка

Рецензент копирует завершённые артефакты в приватный набор со случайными обозначениями, в которых нет задачи, варианта, повтора, имени каталога, текста запроса или лога CLI. HTML, JSON и заметку обновления проверяют вместе. Порядок случайный. Если возможно, не показывайте вариант до фиксации оценок и времени правок.

Полное ослепление маловероятно: полный пакет может создавать узнаваемый viewer и более богатый набор файлов. Попросите рецензента записать, какой вариант он предположил и почему. Узнаваемость стиля renderer укажите как ограничение; не называйте проверку слепой, если это не так.

До оценки верности источникам рецензент читает соответствующий входной файл, затем проверяет каждое представление, существенные подробности, условия веток, связи источников и статусов и выходные файлы. Автоматические проверки структуры, геометрии и чтения JSON могут дополнять проверку, но не определяют смысловую верность, полезность или принятие. Оценки качества остаются человеческими.

Используйте приведённые ниже списки только для рецензента. **Никогда не копируйте их в `input.md`, `prompt.txt` или рабочий каталог попытки.** В них описаны ожидаемые свойства ответа, поэтому они раскрыли бы ответы агенту.

### Список рецензента: `incomplete`

- Сценарий остаётся TARGET / TO-BE и охватывает отправку запроса, решение о доступности ревьюера, публикацию обратной связи и подтверждение прочтения во всех трёх представлениях.
- Предоставленное целевое поведение отмечено как требование или намерение, а не как наблюдаемое текущее поведение.
- Решение «есть/нет доступности» видно с содержательными полными условиями и конечными точками.
- Не придуманы как факты срок ответа, действия при недоступной дате, срок обратной связи и работа с исправленной версией или повторной отправкой. Существенные пробелы локализованы как неизвестные или вопросы там, где они меняют путь.
- Не объявлены установленными эмоции клиента, частота, кадровая система, канал уведомления помимо описанного поведения портала или бизнес-эффект.

### Список рецензента: `current`

- Карта остаётся CURRENT / AS-IS, сохраняет два датированных документа и представляет их содержание как документированные утверждения, а не наблюдения.
- Срок и поля запроса, запись в журнал, проверка закрытой даты, письма с разрешением или отказом, проверка личности на северной стойке, выдача и возврат пропуска прослеживаются до источников.
- Видны ветка закрытой даты и восстановление при несовпадении документа; во втором случае сотрудник звонит хозяину встречи и не выдаёт пропуск.
- Шаблон письма используется только для утверждений, которые он поддерживает. Не придуманы объём, эмоции, ожидание, реализация системы или успешное выполнение в реальности.

### Список рецензента: `conflicting`

- Два датированных источника сохранены раздельно и связаны с утверждениями; более новая FAQ не считается авторитетной только из-за даты.
- Расхождение между немедленным подтверждением с оплатой при получении ключа и подтверждением только после получения депозита видно в затронутом этапе, утверждениях и условиях процесса.
- Сохранены непротиворечивые части: запрос, проверка доступности, ветка отказа, получение и возврат ключа.
- Открытый вопрос называет владельца или решение, необходимое для разрешения конфликта. Артефакт не объединяет две последовательности в неподтверждённый единый текущий путь.

### Список рецензента: `update`

- Карта остаётся CURRENT / AS-IS. ID неизменённых сущностей и точная запись источника `studio-desk-guide` сохранены; новый материал получает отдельную запись источника.
- Планируемая длительность добавлена в запрос, а чек-лист оборудования — перед выдачей ключа, с привязкой к новому источнику.
- Конфликт между возвратом на ресепшен до 17:00 и возвратом только через ящик службы безопасности не разрешён только по дате. Оба источника видны, связанные утверждения, узлы и связи согласованно обновлены, а открытый вопрос фиксирует нужный авторитет.
- Незатронутые этапы, участники, ветки, ID и связи источников не переписаны и не удалены незаметно.
- `changes.md` называет базовую версию и новый источник, изменённые и добавленные ID с причинами, удаления либо явно сообщает об их отсутствии, нерешённый конфликт и действительно проведённые проверки. Он не заявляет визуальные, интерактивные, экспортные или воспроизводимые проверки, если они не выполнялись.

## Якоря оценок

После изучения артефакта поставьте одно целое значение по каждому измерению качества. Для каждой оценки 0 или 1 добавьте краткое свидетельство. Якоря помогают согласовать человеческое суждение и не рассчитываются автоматически.

### Верность источникам

- **2:** Существенные фактические утверждения прослеживаются до предоставленных источников, типы источников и режимы представлены честно, а содержание не отброшено и не опровергнуто незаметно.
- **1:** Основной смысл источников сохранён, но одно или несколько второстепенных утверждений слишком широки, слабо подтверждены или непоследовательно маркированы и не меняют существенное решение.
- **0:** Есть жёсткое неподтверждённое фактическое утверждение, существенное утверждение источника отброшено или ему противоречат, документ представлен как наблюдаемое поведение либо обновление переписывает историю источников. **Любое жёсткое неподтверждённое фактическое утверждение принудительно даёт 0 за верность источникам.**

### Неизвестные и конфликты

- **2:** Существенные пробелы и конфликты явны, связаны с затронутыми этапами или сущностями и сопровождаются полезными вопросами или описанием влияния; авторитет не придуман.
- **1:** Основная неопределённость признана, но не полностью локализована, не все конкурирующие источники связаны или влияние на решение описано неполно.
- **0:** Существенный пробел представлен как известный факт, конфликт разрешён незаметно или критическая неопределённость скрыта от связанного пути.

### Условия и восстановление

- **2:** Решения, полные условия веток, получатели и конечные точки, передачи и описанные пути восстановления согласованы в процессе и остальных представлениях.
- **1:** Основной путь понятен, но условие, конец ветки, передача или восстановление расплывчаты либо представлены непоследовательно.
- **0:** Существенная ветка или восстановление отсутствуют или неверны, условия меняют смысл источника либо показан только предполагаемый успешный путь.

### Читаемость и полезность для решения

- **2:** Рецензент может открыть все три представления, понять границы сценария и различия свидетельств и использовать артефакт для обсуждения указанного решения после не более чем небольших правок.
- **1:** Содержание в целом понятно, но плотность, подписи, расхождения между представлениями, недостающие детали или работа файлов создают заметные затруднения перед использованием.
- **0:** Запрошенное представление отсутствует или непригодно, сценарий невозможно проследить либо артефакт введёт решение в заблуждение без существенной переделки.

Ручные правки и время записывайте отдельно от четырёх оценок качества:

- **Ручные правки:** перечислите необходимые для приемлемого артефакта исправления фактов, источников и статусов, топологии и условий, читаемости, рендеринга и выходных файлов. Запишите число правок и активные минуты. Ставьте `0` только после того, как человек подтвердил отсутствие нужных правок; непроверенные значения оставляйте пустыми.
- **Время запуска:** используйте `elapsedSeconds` runner для сессии Codex. Это значение включает запуск CLI и работу инструментов и не является чистым временем генерации. Не заменяйте тайм-аут его заданным пределом без отметки о цензурированном значении.
- **Время проверки и правок:** отдельно измеряйте человеческую проверку и активное исправление. Паузы и несвязанная работа не входят; отсутствующие измерения остаются пустыми.

## Анализ и отчёт

Раскройте варианты только после фиксации оценок, заметок и времени. Сначала покажите результаты 16 запусков, затем распределение проверенных людьми оценок и сопоставленные наблюдения по задаче и повтору. Для каждой оценки сохраняйте явный знаменатель. При двух повторах на задачу показывайте отдельные значения либо медианы и диапазоны вместо статистики с избыточной точностью.

Закономерности по задачам описывайте как гипотезы для дальнейшей проверки. Не объявляйте пакет превосходящим потому, что он создал больше файлов, прошёл структурную проверку или использовал узнаваемый renderer. Сводное утверждение о превосходстве требует завершённой человеческой проверки по этому протоколу и всё равно должно называться исследовательским: входы синтетические, выборка мала, сессии используют одну среду хоста, а стиль может раскрывать вариант.
